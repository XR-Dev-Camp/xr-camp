## 学习目标

完成本项目后，你将能够：

1. 用**坐标（coordinates）**（x、y、z，单位为米）在 3D 空间中放置物体，并解释每根坐标轴指向哪里。
2. 解释**场景图（scene graph）**：物体是嵌套的，子物体会随父物体一起移动。
3. **变换（transform）**物体：位置、旋转（角度和弧度）和缩放。
4. 选择一种**相机（camera）**：透视相机或正交相机，并解释视场角（field of view）。
5. 用**环境光（ambient）**、**平行光（directional）**和**点光（point）**为场景打光。
6. 解释**材质（material）**如何决定表面对光线的反应方式。
7. 比较 **WebGL**、**three.js**、**A-Frame** 和 **X3D**，描述 Babylon.js、PlayCanvas 和 WebGPU，并为某个项目选出一个，说明理由。
8. 用文字描述任意一个 3D 场景，让信息不再只存在于画面之中。

### 第 1 步：一个 3D 场景由什么组成（TODO 1）

无论叫什么名字，每个 3D 引擎都有相同的组成部分：

| 部分 | 是什么 | 在实验室中 |
| --- | --- | --- |
| **场景（Scene）** | 整个世界：其中一切事物的树状结构 | 房间 |
| **网格（Mesh）** | 一个可见物体：一个**几何体（geometry）**（由三角形组成的形状）加一个**材质（material）**（表面看起来的样子） | 桌子、陶罐、石头 |
| **光源（Light）** | 光从哪里来 | 环境光、太阳光、台灯光 |
| **相机（Camera）** | 你从哪里看，能看到多少 | 你的眼睛 |
| **渲染器（Renderer）** | 用 WebGL 把这一切变成 `<canvas>` 上的像素 | 画面 |

### 第 2 步：渲染（TODO 12）

`renderer.render(scene, camera)` 会绘制一张画面：这个场景，从这个相机看到的样子。仅此而已。

大多数 3D 示例会在一个**动画循环（animation loop）**中每秒绘制 60 张画面，一直持续下去。这个实验室不是这样：没有任何东西会自己运动，所以它只在你改变某个控件时才绘制。这叫做**按需渲染（rendering on demand）**，它能让图形芯片休息，从而节省手机电量。完成 TODO 12，重新加载页面，展品就会出现。

### 第 3 步：坐标（TODO 2）

位置由三个数字组成，**x、y、z**，以**米**为单位，从世界的中心开始测量：

- **x** 从左（负）到右（正）。
- **y** 从下到**上**。地面在 y = 0 处。
- **z** 从远离你（负）到**朝向你（正）**。

实验室中的红、绿、蓝线是**坐标轴（axes）**：x 是红色，y 是绿色，z 是蓝色（RGB = XYZ，一个方便记忆的对应关系）。使用真实尺寸：一张桌子大约高 0.75 米。在 VR 中，尺寸是真实的，一张高 10 米的桌子会让人觉得不对劲。

### 第 4 步：旋转与缩放（TODO 3–4）

**变换（transform）**是一个物体的位置、旋转和缩放。旋转有一个陷阱：

- **three.js 用弧度（radians）测量角度。**一整圈是 2π（约 6.28），直角是 π / 2。
- **A-Frame 和大多数人用角度（degrees）。**一整圈是 360。

滑块给出的是角度，所以需要转换：`THREE.MathUtils.degToRad(90)` 得到 π / 2。忘记这一点是 three.js 中最常见的错误：把桌子「转 90」弧度，会让它旋转超过十四圈。

**缩放（Scale）**会让尺寸倍增：2 是原来的两倍大，0.5 是一半。`setScalar(2)` 会同时在三个方向上缩放。

### 第 5 步：场景图（TODO 5）

场景中的物体是嵌套的，就像 HTML 元素一样。桌子是一个**组（Group）**：一个看不见的父物体，容纳着它的桌面、桌腿、陶罐和石头。当父物体移动、旋转或变大时，它的**子物体（children）**也会跟着一起变化：转动桌子，桌子上的一切也会跟着转动。

子物体的位置是**相对于其父物体**测量的，而不是相对于世界的中心。试一试：在 TODO 5 中，先用 `scene.add(stone)` 把石头从桌子上移走，然后转动桌子，再勾选一次那个复选框。石头会跳动，因为同样的数字现在的含义变成了「相对于桌子」，而不是「相对于房间」。`attach()` 会重新计算这些数字，让石头保持在原地不动。这个区别值得用一整节课来理解。

图片下方的**场景图列表**展示了这棵树。它同时也是场景的 2D 版本：使用屏幕阅读器的人可以在那里探索这个结构。

### 第 6 步：相机（TODO 6）

- **透视相机（perspective camera）**的工作方式像人的眼睛：远处的东西看起来更小。它的**视场角（field of view，FOV）**是它看到的范围有多宽，以角度表示（在 three.js 中，指的是垂直方向的角度）。小的 FOV 类似放大镜头；大的 FOV 能看到更多，但边缘会被拉伸。
- **正交相机（orthographic camera）**让所有物体在任何距离下都保持相同大小，就像建筑师的平面图。适合地图、图表和 2D 游戏。

修改相机的设置后，要调用 `updateProjectionMatrix()`，否则不会有任何变化。

### 第 7 步：灯光（TODO 7–8）

| 光源 | 类似于 | 阴影与形状 |
| --- | --- | --- |
| **环境光（Ambient）** | 到处反弹的光线 | 均匀照亮每一面：完全没有形状感 |
| **平行光（Directional）** | 太阳：从远处射来的平行光线 | 能显示出形状；方向才是关键 |
| **点光（Point）** | 一个灯泡 | 从一个点向四面八方照射，随距离衰减 |

把环境光调到 0：处于阴影中的一面会变黑。把它调到 2：一切看起来都很平。好的布光是一种平衡，通常是一点点环境光加上一两种其他光源。

### 第 8 步：材质（TODO 9）

材质决定表面如何回应光线：

- **基础（Basic）**完全忽略光照：只有单一的平面颜色。绘制成本低，适合界面元素。
- **Lambert** 是哑光的，就像陶土或纸张。
- **标准（Standard）**是**基于物理的（PBR）**：**粗糙度（roughness）**（0 是镜面般的光滑，1 是粉笔般的哑光）和**金属度（metalness）**（0 是油漆或石材，1 是裸露的金属）。大多数现代 3D 模型，包括 glTF 文件，都使用这种材质。

试试把台灯打开和关闭，同时使用**基础**材质：什么都不会改变。这就是判断一个材质是否忽略光照的方法。

### 第 9 步：描述场景（TODO 10–11）

3D 场景是由 JavaScript 绘制出来的一幅画面，屏幕阅读器无法「看到」它内部的内容。所以 XR Camp 的每一节课都有一份**场景描述**：用文字表达同样的信息，并且**从相同的数值**生成，因此它永远不会过时。在这个实验室中，它会说明石头在哪里、桌子转了多少、你正在通过哪个相机观看，以及哪些灯是开着的。

这不仅仅是为了失明的学习者。它也能帮助那些设备较慢、3D 内容无法加载的人，并且能迫使你真正弄清楚自己的场景到底展示了什么。

### 第 10 步：原生 WebGL

打开 `compare/webgl.html`，阅读它的代码。**WebGL** 是浏览器内置的图形 API，由 Khronos Group 制定标准。它对桌子、相机或灯光一无所知：只知道**三角形**，以及两个运行在图形芯片上的微小程序，叫做**着色器（shaders）**。一个负责定位顶点（顶点着色器），另一个负责给像素上色（片元着色器）。

四十行代码，只画出一个平面三角形。实验室中的一切（灯光、材质、相机、场景图）都是成千上万行引擎代码，把你的想法变成三角形和着色器。这正是引擎存在的意义。

### 第 11 步：用 three.js 搭建展品（TODO 14）

**three.js** 是使用最广泛的 JavaScript 3D 库。你在代码中亲手创建每一个物体，然后让渲染器绘制它们。在 `compare/three.html` 中，用尽可能少的代码搭建这个展品，位置和颜色要和实验室中的一致。

### 第 12 步：用 A-Frame 搭建展品（TODO 15）

**A-Frame** 建立在 three.js 之上，但你写的是 **HTML**：`<a-box>`、`<a-cylinder>`。如果你不指定相机和灯光，它会自动添加，还会加上一个 VR 按钮，并且用**角度**来表示旋转。在 `compare/aframe.html` 中搭建同样的展品。哪一种写起来更快？哪一种读起来更容易？

### 第 13 步：X3D，以及测量

打开 `compare/x3d.html`。**X3D** 是 Web3D 联盟制定的 ISO 标准，比 WebGL 更早出现，至今仍用于科学、医疗和文化遗产领域的模型。X3DOM 是一个能在网页中显示 X3D 内容的 JavaScript 库。注意它的嵌套方式：一个 `Transform` 包含一个 `Shape`，`Shape` 又包含一个 `Appearance` 和一个几何体。

现在开始**测量**。用**网络（Network）**面板打开每个页面，重新加载，记录下它下载的库的大小（「已传输」这一列）。同时统计场景代码的行数。把两者都写进你的分析中。

### 第 14 步：研究 Babylon.js、PlayCanvas 和 WebGPU

还有另外三种你应该了解的技术。阅读它们各自的主页和一个示例，做好笔记：

- **Babylon.js**：一个完整的开源引擎，由微软支持，内置物理引擎、编辑器和许多工具。
- **PlayCanvas**：一个带有在线可视化编辑器的开源引擎，在游戏和产品展示领域很受欢迎。
- **WebGPU**：不是一个引擎，而是继 WebGL 之后由 W3C 推出的新一代图形 API。它能更直接地访问图形芯片，包括通用计算。three.js 和 Babylon.js 已经可以使用它。

## 关键代码解析

**`THREE.MathUtils.degToRad(deg)`** 把角度转换为弧度：`deg × π / 180`。

**`parent.attach(child)`** 把 `child` 移动到一个新的父物体，**但不会改变它在世界中的位置**。`parent.add(child)` 会保留它原来的数字，所以它会随之移动。

**`camera.updateProjectionMatrix()`** 必须在任何对 `fov`、`aspect` 或正交相机边界的修改之后调用。

**`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`** 能在高密度屏幕上画出清晰的画面，但绝不会超过两倍的像素：如果一台像素比为 3 的手机不做限制，它绘制的像素数量会比像素比为 2 时多出一倍以上，却几乎看不出更好的效果。

**`new ResizeObserver(…)`** 会在画布所在的容器尺寸变化时重新绘制，而不仅仅是在窗口大小变化时。

**导入映射（import map）**把 `three` 映射到固定版本的 three.js 文件，还把 three.js 自身的 `three.core.js` 映射到它的压缩版本（参见 [`docs/en/3d-assets-and-versions.md`](../../docs/en/3d-assets-and-versions.md)（英文））。

## 3D 与 XR 无障碍

整节课都是关于 3D 的，所以它的无障碍性是内建的，而不是一个单独的环节：

- 每个页面都有一份**场景描述**，实验室中的描述会随你的操作而更新。
- 实验室的**场景图列表**是场景结构的 2D 版本。
- 每个控件都是标准表单控件，带有可见的标签：滑块可以用方向键操作。
- **没有任何东西会自己运动**，除非你改变某个控件，所以没有什么需要暂停，也不会引起晕动症。每个相机都是固定的。

## 性能注意事项

本课最重要的性能经验，是你亲自测量出来的那一条：**库是有下载成本的**。A-Frame 压缩后大约下载 350 KB，three.js 大约 190 KB，原生 WebGL 则不需要下载任何东西。对于预付费手机套餐的用户来说，这个差异是真金白银。选择能完成任务的最小工具，只在需要的页面上加载它。

第二条经验是按需渲染：一个每秒绘制 60 次的场景，即使什么都没有变化，也会让图形芯片一直忙碌，电量持续消耗。阶段 3 的性能课（3.6）会更深入地讲解这一点。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 给 three.js 传入角度 | 桌子疯狂旋转 | 使用 `degToRad` |
| 给 A-Frame 传入弧度 | 桌子几乎不转动 | A-Frame 使用角度 |
| 修改 `fov` 却不调用 `updateProjectionMatrix()` | 没有任何变化 | 修改之后始终要调用它 |
| 该用 `attach` 时用了 `add` | 物体会跳动 | `attach` 会保持它在世界中的位置 |
| 只有环境光 | 一切看起来都很平，没有形状感 | 添加一个平行光 |
| 只有一个平行光 | 阴影面是黑色的 | 添加一点环境光 |
| 使用随意的单位表示尺寸 | 在 VR 中一切都不对劲 | 使用米，采用真实世界的尺寸 |

## 故障排查

**画布是空白的。** TODO 12 还没完成，或者控制台（Console）中有报错。检查你是否通过 `http://` 打开了页面。

**`Failed to resolve module specifier "three"`。** 导入映射缺失，或者出现在模块脚本之后。它必须放在最前面。

**X3D 页面是空白的。** 只有当 X3DOM 的脚本和样式表都加载成功后，它才会绘制内容：在网络面板中检查 `x3dom.js` 和 `x3dom.css`。

**一切都是黑色的。** 没有光线照到物体上：检查灯光的强度，或者用基础材质来测试。

**A-Frame 场景占满了整个页面，或者显示出一个 VR 按钮。** 在 `<a-scene>` 上保留 `embedded` 和 `xr-mode-ui="enabled: false"`。

## 值得认识的女性

**Kelsey Gilbert** 是 Mozilla 的一名图形工程师。她曾担任 Khronos Group **WebGL 2.0** 规范的编辑，并在 2023 年共同主持、2024 年正式主持了 W3C 的 GPU for the Web 工作组，该工作组负责制定 **WebGPU**。

你在本课中读过的原生 WebGL 页面之所以能在每个浏览器中以相同方式运行，正是因为有像她这样的人一行一行地撰写规范，并说服浏览器厂商就此达成一致。你对比表格中的两项技术，都凝结着她的工作成果。

## 标准聚焦

本课中出现了三个标准组织。**WebGL** 是 Khronos Group 的标准，基于 OpenGL ES。**WebGPU** 及其着色语言 **WGSL**，由 W3C 的 GPU for the Web 工作组制定。**X3D** 是一项国际标准，ISO/IEC 19775，由 Web3D 联盟维护。像 three.js 和 A-Frame 这样的库并不是标准：它们是构建在这些标准之上的开源项目，这也是它们能更快迭代的原因，也是 XR Camp 要固定它们版本号的原因。
