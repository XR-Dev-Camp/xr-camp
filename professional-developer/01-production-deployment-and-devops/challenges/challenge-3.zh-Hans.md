# 挑战 3：探索

**进阶选做。** 约 90 分钟。

添加一个预发布（staging）环境，让改动在需要任何人批准生产发布之前，就先能在一个真实的网址上看到。

## 任务

1. 添加一个 `staging` 环境（不设必需的审核人）和一个 `deploy-staging` 任务，让它在 `build` 之后运行，每次推送到 `main` 都会部署到这个环境，与现有的 `approve`/`deploy` 生产路径并行。
2. GitHub Pages 每个仓库只提供一个可访问的站点，所以要给 staging 单独的路径或单独的 Pages 项目：可以把它发布到某个 `gh-pages` 风格分支下的 `/staging/` 路径，让 `actions/upload-pages-artifact` 的 `path` 指向一个同时包含两者的文件夹；或者（更进阶地）把 staging 部署到专门为它单独建立的第二个仓库。
3. 在发布仪表盘中新增一节「Staging vs. production（预发布与生产环境）」，解释两者的区别：staging 自动部署、不需要审批；production 始终会等待一次审批。
4. 确认推送到 `main` 会立刻更新 staging，而 production 仍然会在 `approve` 任务处等待，直到你批准它为止。

## 为什么这很重要

大多数真实团队并不会直接部署到生产环境。预发布环境是让一个团队、或者哪怕只是一位审核人，能够先看到改动上线之后的样子，再决定是否要让公众也看到——这和人工审批关卡是同一个思路，只是提前了一步。

## 完成标准

- [ ] Staging 会在每次推送到 `main` 时自动部署。
- [ ] Production 仍然需要人工审批，未做改动。
- [ ] 仪表盘解释了两者之间的区别。
