Release dashboard: the virtual exhibit

This page is not a live status board: it does not call any API, so it works offline and needs no account. It documents, for a person reading it, what the pipeline in workflows/deploy.yml and workflows/rollback.yml does every time it runs, so a teammate — or your future self — can understand a deployment without reading YAML first.

What is being deployed

The virtual exhibit (from Course 3.7): five 3D objects in a browser, with a full 2D twin and keyboard controls. It is plain HTML, CSS, and JavaScript, so it needs no build step: the pipeline copies it to GitHub Pages as it is.

Pipeline stages, in order

Every push to main, or a run started by hand, works through six jobs. Each one must pass before the next starts.

  1. 1. Validate

    Checks the exhibit's HTML with html-validate, and every link inside it with lychee. Nothing is deployed until the markup and links are sound.

  2. 2. Accessibility audit

    Runs pa11y against app/index.html in headless Chrome, checking WCAG 2.2 AA rules against the rendered page. It cannot see inside the WebGL canvas, so it checks the page around the 3D scene: labels, headings, contrast, and the status regions.

  3. 3. Build

    Packages the exhibit's files with actions/upload-pages-artifact, ready for GitHub Pages. A project with a build step (a bundler, a static-site generator) would run it here and upload its output folder instead.

  4. 4. Manual approval

    The run pauses at the production environment. Nothing deploys until a required reviewer, set up in the repository's Settings, approves the run in the Actions tab. This is the guard against an accidental or unreviewed release.

  5. 5. Deploy

    actions/deploy-pages publishes the built artifact to the live GitHub Pages URL, using the github-pages environment GitHub manages automatically.

  6. 6. Release notes

    When the run was triggered by a version tag (like v1.3.0), gh release create --generate-notes publishes a GitHub Release, with notes built from the commits and pull requests since the previous tag. No extra account or token: gh is already on the runner.

Rolling back

workflows/rollback.yml is a second, separate workflow, started by hand from the Actions tab. Type the tag you want live again (for example v1.2.0); it checks out exactly that tag, rebuilds it, waits for the same manual approval, and redeploys it. Rolling back never rewrites history: it publishes an old, already-tested version again, and adds a note to that tag's release recording when and by whom.

Case study: this repository's own pipeline

The README's "Case study" section reads and explains this repository's own .github/workflows/validate.yml: the workflow that checks every lesson before it can be merged. It is a second, working example of the same ideas above — jobs, needs, and a headless accessibility audit — applied to lesson content instead of a 3D exhibit.

Outside GitHub

GitHub Actions and GitHub Pages are free, but GitHub's own domains are slow or blocked for some visitors in mainland China. Two options are worth knowing about, cautiously: Gitee Go (a CI/CD product on the Chinese platform Gitee, similar in shape to GitHub Actions) can build and deploy to a self-hosted server; and a self-hosted runner lets you keep your workflow files here on GitHub while the machine that runs them sits on a network closer to your audience. Gitee Pages, Gitee's own free static-hosting product, stopped serving in 2024, so it is not an option any more. Check each option's current terms yourself before relying on it: hosting policies change.
