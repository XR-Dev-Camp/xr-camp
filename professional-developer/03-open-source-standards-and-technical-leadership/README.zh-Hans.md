## 学习目标

完成本项目后，你将能够：

1. 解释一个 W3C 社区组（Community Group）与一个正式立项的工作组（Working Group）有何不同，以及一份规范如何在两者之间流转。
2. 创建一个免费的 W3C 账号，并加入一个使命与你之前做过的某个项目相契合的社区组。
3. 按照 W3C TAG 的说明文档（explainer）模板，撰写一份说明文档。
4. 识别并写出一份能让维护者拿到手就能直接处理的规范议题（issue）。
5. 在一个真实的公开仓库上提交一个真实的议题或拉取请求，并记录后续发生的事。
6. 给别人真实的工作成果，留下一条具体、友善且有用的评审意见。
7. 为一个小型开源项目搭建它自主运作所需的基础：治理结构、行为准则，以及一份从 SPDX 许可证列表中选出的许可证。
8. 撰写一份简短的决策记录，并描述你会如何指导下一位加入你项目的人。

### 第 1 步：Web 是如何变成标准的

你在本课程中用过的每一个标签、属性和 API，最初都只是某个人的一个想法，被写下来、被讨论、最终被达成共识。**万维网联盟（World Wide Web Consortium，W3C）**发布正式的推荐轨道（Recommendation Track）：一份**工作草案（Working Draft）**在足够稳定、可以被实现和测试之后，会变成一份**候选推荐（Candidate Recommendation）**（以草案和经过评审的快照形式发布），再经过 W3C 成员组织的正式评审和批准，最终成为一份 **W3C 推荐标准（Recommendation）**。而在这一切发生很久之前，大多数想法都是以更加非正式的方式，从一个**社区组（Community Group）**开始的：任何拥有免费 W3C 账号的人都可以加入，不收会费，也不要求代表某个雇主。一个社区组自己产出的报告并不是标准；它们是一个想法被打磨成型的地方，也许有一天，一个正式立项的工作组会接手它。

其他组织为 W3C 未覆盖的那部分 Web 平台运行着各自不同的流程：**WHATWG** 维护着 HTML 和 DOM 的活标准（Living Standards），**IETF** 发布着支撑 HTTP 和 TLS 的 RFC 文档。它们都有一个本课会直接练习到的共同习惯：都会在公开的 Web 上，像任何一个开源项目一样，接受来自公众的提案、议题和拉取请求。

### 第 2 步：一个免费的 W3C 账号和一个社区组（TODO 1-2）

### 第 3 步：撰写说明文档（TODO 3-6）

**说明文档（explainer）**是在正式规范之前撰写的一份纯语言文档：它存在的意义，是让不具备规范专业知识的人也能读懂，从而让更多人能在改变方向的成本还很低的早期阶段就给出反馈。`starter/explainer-draft.md` 逐节遵循真实、当前有效的 [W3C TAG 说明文档模板](https://w3ctag.github.io/explainer-explainer/)（英文）。开始动笔之前，请先完整地读一遍那个页面：它不仅说明每一节该写什么，还解释了每一节为什么存在。

按顺序完成各节内容：引言、目标、非目标、用户研究、提议的方案、已考虑的替代方案、无障碍/国际化/隐私/安全的综合部分，以及利益相关方反馈。每一份说明文档都需要一个你真正否决过的替代方案，以及一条你真正预期会收到的、具体的反馈，而不是一句含糊的「可能有人会不同意」。

### 第 4 步：提交一份好的规范议题（TODO 7）

一份好的议题会把维护者行动所需的一切都交到他们手上，不用他们再反过来追问：

- **一个议题只谈一个问题。** 一个议题里塞进两个不相关的抱怨，结果往往是比较容易处理的那个先被解决，另一个就被遗忘了。
- **一个具体、可搜索的标题。** 「Clarify recommended practice for X」以后还能找到；「confusing」找不到。
- **给出背景，而不只是提要求。** 说清楚你尝试了什么、期望的是什么、实际发生了什么；如果是文档或规范措辞方面的问题，直接引用你认为该改的那段确切文字。
- **提交前先检查是否已有重复议题。** 在提交之前，先在仓库里搜索一遍已开启和已关闭的议题。

在 `standards-plan.md` 第 4 节里起草你自己的议题。真正把它提交到一个真实仓库上，是本课必做的「基础」挑战（见 [`challenges/challenge-1.zh-Hans.md`](challenges/challenge-1.zh-Hans.md)）。

### 第 5 步：做出一次真实的贡献（TODO 8）

提交一份规范议题是一种贡献；提交一个小而真实的拉取请求是另一种，往往还是个更容易入手的起点。修复一处文档、报告一个失效链接，或者处理一个你已经在用的项目里标着「good first issue」的任务，都是正当的选择。`contribution-record.md` 要求你真实地记录一次这样的贡献：你改动了什么，为什么选它，按照第 4 步的标准它为什么算得上一个好的议题或拉取请求，以及你提交之后发生了什么。

### 第 6 步：评审别人的工作（TODO 9）

评审是一项独立的技能，和写代码不是一回事。一条有用的评审意见会指出具体的东西（某一行、某一个词、某种行为），解释它为什么重要，并且始终保持友善：先假定作者的选择是有原因的，先去询问，而不是先假定那是个失误。找一个真实的、开放中的、不属于你自己工作的拉取请求或议题，仔细读到能够说出具体意见的程度，然后留下一条评论。把你说了什么、后来发生了什么，记录在 `standards-plan.md` 第 6 节里。

### 第 7 步：运营一个小型开源项目（TODO 10-12）

一旦有不止一个人参与，一个项目要想自主运作，光有代码是不够的：

- **治理结构**（`mini-project/GOVERNANCE.md`）说明谁能做什么，以及决定是怎么做出来的。没有它，每一个决定都会变成一场私下的争论，而不是一套已知的流程。
- **行为准则**（`mini-project/CODE_OF_CONDUCT.md`）规定了对每个人的行为期望，同样重要的是，它要指明一条真实的问题举报渠道。采用一个被广泛认可的模板，比如[贡献者公约（Contributor Covenant）](https://www.contributor-covenant.org/)（英文），能让贡献者大致知道会遇到什么。
- **许可证**让这个项目在法律上真的能被使用。没有它，版权默认就是「保留所有权利」，无论仓库看起来多么公开，其他任何人在法律上都不能使用、复制它，或为它做贡献。[SPDX 许可证列表](https://spdx.org/licenses/)（英文）为每一种许可证提供了一个简短、精确的标识符（`MIT`、`Apache-2.0`、`GPL-3.0-only`），工具和人都能一眼核对；把你的选择写成一份**决策记录**，放在 `mini-project/decision-record-0001-choose-a-licence.md` 里。

### 第 8 步：技术领导力：决策记录与指导新人（TODO 13）

一份**决策记录**（有时也叫架构决策记录，Architecture Decision Record，ADR）是一份简短、标注日期的记录，记下一个决定、它的背景和它带来的后果，这样后来加入的人不用去问做决定的人，也能理解这个选择。你在第 7 步为选择许可证已经写过一份；这个习惯可以推广到任何值得被记住的决定上。技术领导力的另一半更安静：你如何对待接下来出现的那个人。在 `standards-plan.md` 第 8 节里写下：如果有人加入你所选的社区组，或者加入你的小型项目，你会怎样指导他们，以及你会怎样对他们的第一个拉取请求给出反馈。

### 第 9 步：无障碍的计划页面（TODO 14-15）

以上内容都存在于 Markdown 文档里；最后一步把它们呈现为一个小型的、无障碍的网页，让一位评审者、导师，或未来的雇主不需要下载任何东西就能打开查看。构建 `index.html`，为计划的每一部分设一个 `<section>`，各自带有自己的标题，并把每一节都链接回它所概括的那份文档，而不是把那份文档的内容整段重复一遍。

## 关键代码解析

- **社区组与工作组的区别。** 社区组向任何拥有免费 W3C 账号的人开放，产出的报告本身不具有正式地位；工作组由 W3C 的成员组织正式立项，是唯一能够把一份规范推进到推荐轨道上的组织形式。
- **W3C 社区贡献者许可协议（CLA）。** 每一位社区组参与者都要接受的协议，涵盖所贡献材料的版权条款，以及一项免版税的专利许可承诺。这是一份真实的、具有约束力的协议，不是一道可以随手跳过的形式关卡。
- **说明文档（Explainer）。** 一份在正式规范之前撰写的纯语言文档，其职责是让不具备规范专业知识的人也能对一个想法进行评审，从而在问题还便宜易改的阶段就把它们暴露出来。
- **`aria-describedby`。** 一个已经存在的、普通的 HTML/ARIA 属性，从一个元素指向描述它的文字；参考答案中的说明文档提议的是按名字推荐使用它来处理 3D 场景，而不是发明一个新属性。
- **SPDX 标识符。** 一个简短、精确的字符串（`MIT`、`Apache-2.0`），明确无歧义地指代某一种具体的许可证，这样工具或人就永远不必猜测一个项目所说的「类似 MIT 的许可证」到底是哪一种。
- **决策记录。** 一份简短、标注日期的记录，包含状态、背景、决定和后果几个部分，写出来是为了让一个选择，对当时不在场的人依然是可以理解的。

## 无障碍要求

| 要求 | WCAG 2.2 | 原因 |
| --- | --- | --- |
| 声明了文档语言 | 3.1.1 | 屏幕阅读器据此选择正确的发音和语音 |
| 每一节只有一个 `<h1>`，标题层级顺序合理 | 2.4.6、1.3.1 | 让屏幕阅读器用户能按标题浏览这份计划，就像视力正常的读者浏览时那样 |
| 每个链接的用途都能从文字或上下文中看清楚 | 2.4.4 | 「Read the full explainer draft」能告诉屏幕阅读器用户他们将得到什么；「click here」不能 |
| 用 `list-style: none` 设置样式的列表仍保留 `role="list"` | 1.3.1 | 一旦没有了项目符号，Safari 会去掉列表隐含的列表语义，其他浏览器没有这个问题 |
| 每个链接的焦点都可见 | 2.4.7 | 键盘用户必须始终能看到自己所在的位置 |
| 颜色对比度达到 AA 级 | 1.4.3 | 状态文字（「Done」「Planned」）必须是可读的，而不只是装饰性的 |
| 状态从不只靠颜色表达 | 良好实践 | 「Done」和「Planned」都是文字，而不只是不同的颜色 |

## 性能注意事项

本课的交付物是文字：Markdown 文档，加上一个小型 HTML 页面，没有图片、没有 3D、没有 JavaScript。它全部的体积就是一份和本课程其他部分共享的样式表。这里没有什么需要优化的东西；真正重要的纪律，是让每一份文档都足够简短，简短到一位很忙的维护者真的会去读它——这本身也是一种「性能」。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 把一份社区组的报告当作推荐标准 | 声称某个功能已经「标准化」，而它其实还没有通过正式评审 | 说「正在 \<名称\> 社区组中讨论」，并核实它实际的状态 |
| 提交一份含糊的议题（「这个不好用」） | 维护者不得不追问好几个问题，或者干脆把它关闭 | 给出具体的标题、确切的背景，以及你原本期望发生的事 |
| 撰写说明文档时只有一份 API 草图，没有目标或替代方案 | 评审者无法判断它解决了什么问题，也无法判断是否存在更简单的解法 | 按顺序完成真实模板中的每一节 |
| 照抄一个你喜欢的项目的许可证，却没有读过它 | 你可能因此承诺了一些你本不打算承诺的事（比如把所有改动都回馈开源） | 选定一个确切的 SPDX 标识符，并把这个取舍写成一份决策记录 |
| 行为准则里只写「联系维护者」，却没有具体的联系方式 | 一份举报根本无处可去 | 指明一条具体的、有人监看的举报渠道 |

## 故障排查

**好像没有一个社区组适合我。** 去 [w3.org/community](https://www.w3.org/community/)（英文）浏览完整列表，而不只是那些知名的；那里有成百上千个，涵盖各种细分主题。如果实在没有合适的，四个人可以一起提议成立一个新的。

**一个拉取请求评审机器人要求你签署某样东西。** 许多真实仓库会在第一个拉取请求上自动运行贡献者许可协议或开发者原创声明（Developer Certificate of Origin，DCO）检查。在同意之前先读清楚它到底要求什么；这是正常且预期之内的，并不代表你做错了什么。

**你的 `index.html` 没有通过链接检查。** 从 `completed/index.html` 指向 `mini-project/` 里某个文件的相对链接，路径中需要包含文件夹名（`mini-project/GOVERNANCE.md`），而不能只写文件名。

**无障碍检查工具标记了一个列表。** 如果你添加了一个用 `list-style: none` 设置样式的 `<ul>`，却没有加上 `role="list"`，Safari 上的 VoiceOver 会把它当作没有任何列表语义的纯文本朗读出来；Chrome 和 Firefox 的屏幕阅读器支持没有这个缺口，这正是它容易在测试中被漏掉的原因。

## 标准聚焦

这整节课本身就是「标准聚焦」。**W3C** 通过其流程文档发布正式的推荐标准，让一份规范经过工作草案和候选推荐（草案和经过评审的快照）阶段，再由其成员组织完成最终评审；它的**社区组**在更早、更非正式的阶段工作，向任何拥有免费账号的人开放，遵循一份涵盖版权和专利的社区贡献者许可协议。其他机构为 W3C 未涉及的那部分平台运行着各自的轨道：**WHATWG** 维护 HTML 和 DOM 的活标准，**IETF** 发布支撑这一切底层网络协议的 RFC 文档。它们每一个都会接受来自公众的议题和拉取请求，这正是为什么课程 2.7 里的技能和本课的技能并不是两件不同的事：它们是同一种技能，只是这次瞄准的是 Web 平台本身，而不是某一节课的项目。
