## 学习目标

完成本项目后，你将能够：

1. 把一份已获批准的简报转化为具体的用户旅程。
2. 为你的毕业设计所需的屏幕或场景绘制线框图。
3. 在动手构建之前，先在纸上设计一个 3D 或 XR 场景的空间布局。
4. 绘制一张场景图：实体、层级结构，以及它们之间的关系。
5. 为你项目的内容设计一个简单的数据模型。
6. 勾勒出你的前端需要的 API，哪怕它只是一个小型的本地 API。
7. 撰写一份适合小型免费工具项目的安全与隐私计划。
8. 撰写一份测试计划，说明你之后将如何检查无障碍性、性能和本地化情况。

## 先决条件

- **第 7.1 阶段：毕业设计研究与定义。** 在开始这个阶段之前，你需要有一份已获批准的简报、利益相关方图谱和导师批准。
- 如果你的毕业设计需要用到，还需要**课程 5.4：实时与多用户应用**和**课程 5.5：空间应用的安全与隐私**。

## 你将构建什么

专业毕业设计的第二阶段：在写下任何生产代码之前，为你已获批准的毕业设计产出**完整的设计**。你会产出八份文档：用户旅程、线框图指引、空间布局、场景图、数据模型、API 草图、安全计划和测试计划。

[`completed/`](completed/) 中的参考答案，延续了 Ana 在第一阶段的 Aurora 社区博物馆展览：一个单独的展厅、一条访客旅程，以及一个针对少量物品、诚实而简单的数据模型。[`completed/index.html`](completed/index.html) 把全部八份文档呈现出来。起始代码有同样的八份模板，一共 10 个 TODO，还有这个阶段的评分标准。

### 第 1 步：用户旅程（TODO 1-2）

打开 [`starter/journeys.md`](starter/journeys.md)。一条用户旅程，是一位真实的人为了达成一个目标而经历的一串编号步骤：到达、决定要做什么、采取行动，并带着他们想要的东西离开。为你的主要受众写一条旅程（TODO 1），再为你第一阶段图谱里的另一位利益相关方——比如维护这个项目的人——写一条旅程（TODO 2）。

### 第 2 步：线框图（TODO 3）

打开 [`starter/wireframes.md`](starter/wireframes.md)。线框图是一个屏幕或场景布局的粗略草图，没有颜色，也不追求精美：只有方框、标签和箭头。为你范围内的每一个屏幕或场景在纸上或简单工具里画一张草图，然后在这份文件里用文字描述每一张草图（一张纸质草图的照片，用文字描述出来，在这里完全可以接受——这份模板要求的是描述，而不是图片本身）。

### 第 3 步：空间布局（TODO 4）

打开 [`starter/spatial-layout.md`](starter/spatial-layout.md)。对于一个 3D 或 XR 毕业设计，在动手构建之前先规划好这个空间：相机或访客的起始位置在哪里，他们最先能看到什么，物体之间相距多远，他们接下来会走向哪里或看向哪里？一份简单的 ASCII 平面图，就像 `web3d-developer` 里用的那种，就足够了。

### 第 4 步：场景图（TODO 5）

打开 [`starter/scene-graph.md`](starter/scene-graph.md)。场景图是一棵树：场景中的每一个实体，以及它的父级是哪一个实体。在写代码之前先画出它，能提前告诉你哪些东西会一起移动（子实体会跟着父实体移动），以及你的代码将需要创建和更新哪些东西。

### 第 5 步：数据模型（TODO 6-7）

打开 [`starter/data-model.md`](starter/data-model.md)。列出你的毕业设计需要的每一种内容类型（TODO 6）——对 Ana 来说，这是「展品对象」，带有标题、描述和材质等字段。然后为每种类型描述字段和关系（TODO 7）：哪些是必填的，哪些是可选的，各类型之间又是如何关联的。

### 第 6 步：API 草图（TODO 8）

打开 [`starter/api.md`](starter/api.md)。即便一个毕业设计没有服务器，也需要知道它的前端在什么时候请求什么数据。把它勾勒成一份简短的清单：一个函数名或接口，它需要什么，返回什么——不论这是一个真实的 HTTP 接口，还是一个读取本地 JSON 文件的函数。

### 第 7 步：安全与隐私计划（TODO 9）

打开 [`starter/security-plan.md`](starter/security-plan.md)。直白地说明你的毕业设计收集了哪些个人数据（如果有的话）、存储在哪里，以及谁能看到它们。一个除了匿名访问之外什么都不收集的项目，应该明确地这样声明——对一个小型免费工具项目来说，这是一个有效、而且往往是最好的答案。

### 第 8 步：测试计划（TODO 10）

打开 [`starter/test-plan.md`](starter/test-plan.md)。在第三阶段开始之前，写下你将如何测试这个原型：哪些无障碍检查（屏幕阅读器、键盘、减少动态效果）、哪种性能预算，以及你会检查哪些语言的本地化就绪程度——即便真正的翻译工作要等到以后才做。

## 关键代码解析

- **用户旅程。** 一位真实的人所经历的一串编号步骤，从带着一个目标到达，到带着已经达成的目标离开（如果你也在梳理一条失败路径，则是没有达成）。
- **场景图。** 一棵实体树，每一个子实体都继承其父级的位置和旋转角度——这和 A-Frame 与 three.js 在运行时使用的结构是同一种。
- **数据模型。** 你内容的形状：存在哪些类型，每种类型有哪些字段，以及各类型之间如何关联，与任何具体的数据库或格式无关。
- **API 草图。** 你的前端会发出的请求清单，用它们需要什么、返回什么来描述，而不必先决定它们具体如何实现。
- **安全与隐私计划。** 一段简短、诚实的声明，说明收集了什么数据、数据存放在哪里、谁能访问它——即便答案是「什么都没有」。

## 3D 与 XR 无障碍

这个阶段规划的是无障碍性，而不是测试它，但这些计划很重要：一个只假设指针输入的空间布局，或一张对视觉场景没有描述替代方案的场景图，日后无法在不重新设计的情况下变得无障碍。在撰写 `spatial-layout.md` 和 `scene-graph.md` 时，为每一项交互记下：它看起来是什么样的，键盘或按钮操作的等效方式又是什么？你的 `test-plan.md` 应该列出具体的人工 3D/XR 检查项（场景描述、键盘路径、减少动态效果、2D 后备方案、舒适度），供第三阶段有了可运行的原型之后使用。

## 无障碍要求

| 要求 | WCAG 2.2 | 原因 |
| --- | --- | --- |
| `completed/index.html` 声明了 `lang="en"` | 3.1.1 页面语言 | 辅助技术需要知道该应用哪种语言规则 |
| 全部八份链接文档中的标题都遵循合理的顺序 | 1.3.1 信息与关系 | 屏幕阅读器用户靠浏览标题来导航 |
| 每张表格都有标题（caption）和 `<th scope>` | 1.3.1 信息与关系 | 表格结构必须能被程序读取 |
| 链接描述其目的地（「Read the data model」，而不是「click here」） | 2.4.4 链接目的（在上下文中） | 仅凭链接文字本身，就应该能说明这是一份什么样的文档 |
| 所有文字的颜色对比度都达到 4.5:1 | 1.4.3 对比度（最低要求） | 低对比度的文字，对许多用户来说是不可读的 |

## 性能注意事项

设计文档在运行时不消耗任何成本，但 `spatial-layout.md` 和 `scene-graph.md` 中的决定，设定了你第三阶段的性能预算。现在就记下一个大致的三角形数量和绘制调用目标（正如 `web3d-developer/06` 所教的那样），这样第三阶段就有一个可以对照测试的数字，而不是事后才去猜测。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 在写用户旅程之前就先设计屏幕 | 屏幕解决的是一个没人提出过的问题 | 先写旅程；让它来决定每个屏幕需要展示什么 |
| 因为「只是一个物体」而跳过场景图 | 第三阶段的代码对物体之间如何关联没有任何规划，会越写越混乱 | 即便场景很小，也画出这棵树；它会随着场景变大而一直有用 |
| 一份只写着「没什么可担心的」的安全计划 | 真实的数据实践（统计分析、本地存储、表单）无人审视 | 先列出每一个收集或存储数据的地方，哪怕简短，再判断它是否低风险 |
| 在第三阶段构建完之后才写测试计划 | 测试变成一件事后才想起的事，问题的修复成本很高 | 现在就写测试计划，这样第三阶段的构建能把它考虑进去 |
| 从一个不相关的项目照搬数据模型 | 不适合你内容的字段，会让之后的工作更难做 | 为你自己内容的真实字段建模，哪怕这份清单很短 |

## 故障排查

**我不知道怎么画场景图。** 从最上层开始：你的 `<a-scene>` 或 three.js 的 `Scene`。为每一个实体加一行，缩进在其父级下面。如果一个物体和另一个物体一起移动或旋转，它就是那个物体的子实体。

**我的数据模型一直在膨胀。** 回去看你第一阶段的「不在范围内」清单。如果某个字段只是为了支持一个你已经决定不做的功能，就把它删掉。

**如果我没有服务器，不确定 API 草图里该写什么。** 列出加载或保存你内容的本地函数（例如，「loadExhibits()：读取 `data/exhibits.json`，返回一个展品对象数组」）。重要的是它的形状，而不是它是本地的还是远程的。

## 拓展挑战

## 标准聚焦

**W3C 的 WAI-ARIA 1.2** 规范和 **OWASP 十大风险**（一份由社区维护的、最常见的 Web 应用安全风险清单）都值得在设计阶段就了解。ARIA 的设计模式会在你写代码之前，就告诉你一个自定义控件需要哪些角色和状态属性；OWASP 清单会告诉你，即便对一个小型免费工具项目而言，你的安全计划也应该规划针对哪些方面的防御。
