# 毕业设计研究与定义

**Language / Idioma / 语言:** [English](README.md) · [Español](README.es.md) · [简体中文](README.zh-Hans.md)

**课程：** `capstone` · **课时：** `capstone-research-and-definition-01` · **时长：** 约 8 小时 · 11 次学习，每次 45 分钟 · 每周 4 次，约 3 周

---

> 产出一份获得批准的毕业设计简报。

---

## 学习目标

完成本项目后，你将能够：

1. 选择一个你能够切实完成的毕业设计项目，并解释它为什么重要。
2. 撰写一份一页纸的简报，说明问题、受众和范围。
3. 梳理你的利益相关方：谁使用它，谁批准它，谁在你之后维护它。
4. 清楚地说明哪些不在范围之内，以及为什么。
5. 为一个空间 Web 项目找到一个真实或合理设想的合作方（非政府组织、博物馆、学校或图书馆）。
6. 在动手构建任何东西之前，先获得书面的导师批准。
7. 像你在课程 2.3 中做过的那样，为一个长期项目规划自己的学习节次。

## 先决条件

- **课程 6.4：职业发展与专业实践。** 你已经有一份作品集，也有一个关于接下来要做什么的计划。
- **课程 3.6：Web3D 性能工程**，或一门同等的 web3D/XR 课程——如果你的毕业设计会包含一个 3D 或 XR 原型（第 7.3 阶段假定你已具备这一基础）。

## 你将构建什么

这是**专业毕业设计**五个阶段中的第一阶段，带领一个真实的空间 Web 项目从构想走向发布。在这个阶段，你不会写任何应用代码。你要写一份**毕业设计简报**、一份**利益相关方图谱**，并获得**导师批准**——这是之后每一个阶段都要建立在其上的三份文档。

你有两种选择：

1. **延续虚拟展览。** 把你在第三阶段（`web3d-developer/07`）搭建的展览，变成一个真正的毕业设计：一个面向社区博物馆的虚拟文化展览，用这个毕业设计所教的产品思维、系统设计和生产级质量把它扩展开来。
2. **一个新的合作方项目。** 为一个真实或合理设想的合作方——一个非政府组织、一座博物馆、一所学校或一间图书馆——提议一个空间 Web 项目。把范围控制得足够小，能在五个阶段内完成。

[`completed/`](completed/) 中的参考答案，讲述了虚构的 XR Camp 学习者 Ana，为她所在城市一个虚构的社区博物馆策划虚拟展览的过程。她的简报、利益相关方图谱和导师批准都已完整填好，你可以看看「完成」是什么样子；[`completed/index.html`](completed/index.html) 把这三者并排展示出来。起始代码有三个 Markdown 模板，一共 6 个 TODO，还有一份评分标准，告诉你每个质量等级看起来是什么样的。

### 第 1 步：选择你的项目和受众

一个毕业设计的好坏，取决于它背后的问题有多好。在动笔之前，先大声回答一个问题：**这是为谁而做的？这个项目会让他们能够做到哪些他们今天还做不到的事？**

如果你打算延续虚拟展览，你的受众已经存在：那些无法亲自前往社区博物馆的访客，或者想在参观之后再次回顾某个展览的人。如果你打算提议一个新的合作方项目，就把这次学习完全花在构思这个想法上。好的毕业设计想法有三个共同点：一个真实的受众、一个能在五个阶段的兼职工作量内完成的范围，以及一个 Web 与 3D 或 XR 真正能带来帮助的理由（而不只是「因为这样很酷」）。

### 第 2 步：问题陈述（TODO 1）

打开 [`starter/brief.md`](starter/brief.md)。TODO 1 要求写一份**问题陈述**：两三句话，说明受众、他们的问题，以及为什么这个问题现在很重要。把它写成是在向一个从未见过你的人解释。避免使用「创新」或「革命性」这类词——一份导师无法评估的简报，也就无法被批准。

### 第 3 步：范围，包含和不包含（TODO 2-3）

TODO 2 列出你在这五个阶段中**会**构建的内容。TODO 3 同样重要：你**不会**构建什么，以及为什么。每一个超出时限的毕业设计，都跳过了这一步。现在就用书面形式说清楚三项你要砍掉的内容，才能让你以后拒绝新增需求时，不会觉得那是一种失败。

### 第 4 步：找一个合作方（真实或合理设想的）

心里有一个合作方，会让毕业设计更扎实，哪怕只是一个紧贴某类真实组织建模出来的假设对象。适合空间 Web 毕业设计的合作方类型：想要一个虚拟展览的**本地博物馆或文化遗产地**，想要向捐赠者说明自己工作的**非政府组织**，想要一个互动学习空间的**学校或图书馆**。除非对方真的同意了，否则不要把某个真实组织写得像是他们已经答应了这个项目。在简报里写「一个小型社区博物馆，类似于〔某类场所〕」，既诚实又依然有用。

### 第 5 步：利益相关方图谱（TODO 4-5）

打开 [`starter/stakeholder-map.md`](starter/stakeholder-map.md)。一份利益相关方图谱，要回答对每一个接触这个项目的人或群体而言：他们对这个项目有什么需求，他们能决定什么，你要如何联系到他们？TODO 4 要求你列出每一位利益相关方——访客、合作组织、你的导师，以及在你完成之后维护成果的任何人。TODO 5 要求你记录你将如何与每一位沟通，以及沟通的频率。

### 第 6 步：风险和悬而未决的问题

每一个真实的项目都有你目前还不知道的事情。在简报里坦率地把它们列出来：一项技术风险（「我还没有确认博物馆的照片是否可以免费使用」）、一项范围风险（「合作方可能想要的东西超出五个阶段所能容纳的」），或一项技能风险（「我以前没有搭建过多用户场景」）。在简报里说出一项风险，不是一种弱点；日后因为漏掉某项风险而让项目脱轨，才是。

### 第 7 步：请求导师批准（TODO 6）

打开 [`starter/mentor-approval.md`](starter/mentor-approval.md)。填好摘要字段，然后把你的简报和利益相关方图谱发给你的导师（如果你还没有导师，就发给一位同学、讲师，或其他值得信赖的审阅者）以获得书面批准。把他们的决定和任何附加条件记录在这个文件里。在这个文件写着「已批准」或「有条件批准」、并且你已经完成相应修改之前，不要开始第二阶段（`02-experience-and-system-design`）。

## 关键代码解析

- **问题陈述。** 导师、合作方或未来的队友，在读完一遍你的简报之后，能够准确复述出来的那一句话。
- **范围，包含和不包含。** 两份清单，而不是一份：你会构建什么，以及你刻意不构建什么。第二份清单，正是保护你的五个阶段不会无限膨胀的东西。
- **利益相关方。** 任何受这个项目结果影响、或能够影响这个项目结果的人——不仅仅是使用它的人。
- **导师批准。** 一份书面的、标注日期的签字确认记录，附带任何条件。它是「一个想法」和「一个已确定的项目」之间的关卡。
- **合作方项目。** 一个你的毕业设计所服务的真实或合理设想的组织。它完全可以是假设出来的，只要你的简报对此如实说明。

## 3D 与 XR 无障碍

这个阶段不产出任何代码，所以目前还没有什么可以在屏幕阅读器中测试的东西。但你在这里做出的选择，决定了你的毕业设计以后能有多无障碍。在撰写问题陈述和范围时，用与无障碍相关的措辞记下你的受众是谁：他们使用屏幕阅读器吗，他们有稳定的宽带吗，他们能流利地阅读你的语言吗？第二阶段会把这些记录变成具体的无障碍要求，所以现在就趁着记忆还新鲜，把它们记下来，哪怕只是简报里的一个要点。

## 无障碍要求

| 要求 | WCAG 2.2 | 原因 |
| --- | --- | --- |
| `completed/index.html` 声明了 `lang="en"` | 3.1.1 页面语言 | 辅助技术需要知道该应用哪种语言规则 |
| 每个标题都遵循合理的顺序（h1，然后是若干 h2，不跳级） | 1.3.1 信息与关系 | 屏幕阅读器用户靠浏览标题来寻找内容 |
| 指向三份文档的链接是可见的文字，而不是「点击这里」 | 2.4.4 链接目的（在上下文中） | 仅凭链接文字本身，就应该能说明这是一份什么样的文档 |
| 每个链接的焦点都可见 | 2.4.7 焦点可见 | 键盘用户需要看到自己所在的位置 |
| 所有文字的颜色对比度都达到 4.5:1 | 1.4.3 对比度（最低要求） | 低对比度的文字，对许多用户来说是不可读的 |

## 性能注意事项

`completed/index.html` 是一个轻量的单页面，只有链接和摘要：没有构建步骤，没有图片，除了共享样式表之外没有任何脚本。保持这样——这个阶段关注的是文档本身，而不是列出它们的那个页面。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 用含糊、营销式的语言撰写简报 | 一份导师无法评估的简报，也就无法被批准 | 使用直白、具体的句子：谁、什么问题、什么范围 |
| 跳过「不在范围内」清单 | 项目会不断膨胀，直到第四阶段时间不够用 | 用书面形式说明至少三项你不会构建的内容 |
| 在获得批准之前就开始写代码 | 一旦简报发生变化，之前的工作就会被丢弃 | 等到 `mentor-approval.md` 中写明「已批准」或「有条件批准」 |
| 把一个尚未同意的真实组织写进去 | 谎报了一段并不存在的合作关系 | 改为描述一个合理设想的合作方类型，直到有真实对象确认为止 |
| 把利益相关方图谱当作一种形式走过场 | 后续阶段会漏掉某位决策者的要求 | 写清楚每一位利益相关方实际能决定什么 |

## 故障排查

**我没有导师。** 改用一位同学、讲师，或值得信赖的审阅者，并在 `mentor-approval.md` 中如实说明。重点是让计划得到一次外部审视，而不是某个特定的职位头衔。

**我的合作方想法一直在膨胀。** 回到第 3 步，往你的「不在范围内」清单里再添几项。一个试图服务每一位可能的利益相关方的毕业设计，很少能把任何一位真正服务好。

**模板打不开。** Markdown 文件可以在任何文本编辑器中打开；它们不需要本地服务器。`starter/index.html` 确实需要一个（`http://`，而不是 `file://`），因为它通过相对路径链接到其他文件。

## 拓展挑战

三个拓展挑战，位于 [`challenges/`](challenges/)。基础挑战为必做，另外两个为选做：

1. **[基础](challenges/challenge-1.zh-Hans.md)**：为你的毕业设计写一段「电梯演讲」，说出光靠利益相关方图谱说不出来的东西——你的项目「为什么是现在」。
2. **[创意](challenges/challenge-2.zh-Hans.md)**：把简报扎根在你自己的语言、社区或文化中：描述你的毕业设计如何体现出你亲身了解的一个地方或社区。
3. **[探索](challenges/challenge-3.zh-Hans.md)**：采访一位贴近你预期受众的真实的人（朋友、家人或同学），并在简报中加入一段来自他们的直接引用。

## 提交作业

1. 完成 [`tests/checklist.md`](tests/checklist.md)。
2. 拍摄一张截图，展示你完成的 `mentor-approval.md` 中的批准决定。
3. 把你的简报、利益相关方图谱和导师批准记录，保存在你的学习日志和作品集中。等 XR Camp 社区上线后，也在那里分享它们。
4. 学习日志问题：在你的简报里，你最没有把握的那一项要求是什么？要怎样才能对它更有把握？

## 标准聚焦

由网络无障碍倡议（Web Accessibility Initiative）发布的 **W3C 网页内容无障碍指南（WCAG）2.2**，是你的毕业设计最终会被评判的标准，从你在这个阶段的简报中写下的无障碍说明开始。之后的阶段会检验具体的成功标准；而这个阶段，正是你第一次用书面形式承诺去满足它们的地方。
