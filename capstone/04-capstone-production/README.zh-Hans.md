# 毕业设计生产构建

**Language / Idioma / 语言:** [English](README.md) · [Español](README.es.md) · [简体中文](README.zh-Hans.md)

**课程：** `capstone` · **课时：** `capstone-production-04` · **时长：** 约 28 小时 · 38 次学习，每次 45 分钟 · 每周 4 次，约 10 周

> **这是一节较长的课程（38 次学习）。** 一步一步来：每次学习仍然会以一个你亲手完成的成果结束，步骤之间休息一下也完全没问题。

## 学习目标

完成本项目后，你将能够：

1. 把一个已获批准的原型和设计，转化为一份生产构建计划。
2. 按照一份构建检查清单推进工作，而不会迷失方向。
3. 撰写一份陌生人也能用来运行和理解你项目的文档。
4. 在构建过程中持续维护一份变更日志，而不只是在发布时才写。
5. 把第二阶段的无障碍、性能和安全计划应用到真正的生产代码中。
6. 在把工作视为完成之前，对照一份质量检查清单自我审阅。
7. 用你第一阶段的「不在范围内」清单作为参考，学会在必要时削减范围，而不是牺牲质量。

## 先决条件

- **第 7.3 阶段：毕业设计原型。** 在开始这个阶段之前，你需要有一个已获批准、经过测试的原型和设计评审记录。
- 与你毕业设计所选技术相关的、之前所有 XR Camp 课程。

## 你将构建什么

专业毕业设计的第四阶段：遵循你第二阶段的设计和第三阶段原型的发现，构建你毕业设计的**生产版本**。这是最长的一个阶段——38 次学习——因为仔细地构建，比规划或制作原型要花更长的时间，而如果急于求成，就会抵消前三个阶段的价值。

与其再做一次示范构建（那只会在更大的规模上重复第三阶段的模式），[`completed/`](completed/) 中的参考答案，是 Ana **填好的生产文档**：她完成的构建检查清单、一份用户指南、一份陌生人也能照着做的 README，以及一份在整个构建过程中持续维护的变更日志。[`completed/index.html`](completed/index.html) 把这四者都展示了出来。起始代码有同样的四份模板，一共 8 个 TODO，还有这个阶段的评分标准。

### 第 1 步：构建检查清单（TODO 1-3）

打开 [`starter/build-checklist.md`](starter/build-checklist.md)。把你第二阶段的设计拆解成小而可检验的任务（TODO 1），按领域分组——场景、数据、无障碍性、性能（TODO 2）——并排好顺序，让基础性的任务排在依赖它们的任务之前（TODO 3）。一份你真的能够逐项打勾的清单，能让一个 38 次学习的构建过程不至于变得毫无章法。

### 第 2 步：构建

这不是分步讲解中的单独一步：它占据了这个阶段的大部分时间。按照你的检查清单，一次处理一项，并像第三阶段教过你的那样边做边测试——键盘、屏幕阅读器、减少动态效果和性能，要持续地应用，而不是留到最后才做。在你的毕业设计需要的地方，复用第三阶段和 `web3d-developer/07` 中的无障碍 3D 页面模式和固定版本的库。

### 第 3 步：用户指南（TODO 4-5）

打开 [`starter/user-guide.md`](starter/user-guide.md)。为真正会使用你毕业设计的人撰写说明（TODO 4）——通俗的语言，不假定任何技术知识——并为在你之后维护它的人撰写说明（TODO 5），包括任何维护者需要知道、但从代码本身看不出来的事情。

### 第 4 步：README（TODO 6-7）

打开 [`starter/readme-template.md`](starter/readme-template.md)。撰写一份 README，让一个陌生人能从零开始把你的项目在本地运行起来（TODO 6），再写一小节说明它用了哪些技术、为什么用它们（TODO 7）。这和本仓库中每一个 `README.md` 遵循的是同一种规范。

### 第 5 步：变更日志（TODO 8）

打开 [`starter/changelog.md`](starter/changelog.md)。在构建过程中，为每一次有意义的改动保留一条标注日期的记录，而不是在最后凭记忆重建。一份诚实维护的变更日志，往往是你在撰写第五阶段案例分析时，回答「我在这个阶段究竟做了什么」最快的方法。

## 关键代码解析

- **构建检查清单。** 一份被拆解成小而有序、可检验任务的生产计划——这正是「构建这个应用」和一份你真的能在 38 次学习中追踪进度的计划之间的区别。
- **用户指南。** 为使用你完成的毕业设计的人撰写的说明，用通俗语言写成，不假定任何技术背景。
- **README。** 任何人——一个陌生人、未来的雇主、未来的你自己——为了理解和运行你的项目而阅读的第一份文档。
- **变更日志。** 一份标注日期、持续更新的记录，记下改动了什么、为什么改，随着过程实时维护。
- **中期构建复查。** 在一次漫长的构建过程中特意安排的一次暂停，用来对照更早的计划重新测试，在问题累积之前就先发现回归。

## 3D 与 XR 无障碍

第二、三阶段的一切现在都要在完整规模上构建出来：每一个场景都需要 `#scene-description`、一份始终存在的 2D 等效内容、每一项交互的键盘路径、任何动画开始前的减少动态效果检查、一个能用的暂停按钮，以及不出现任何未经请求的相机移动。在这个阶段的规模下，每完成一次重要的新增——一个新物体、一项新交互、一个新展厅——就重新测试一次，而不是等到整个构建都完成之后才去检查。

## 无障碍要求

| 要求 | WCAG 2.2 | 原因 |
| --- | --- | --- |
| 每一个生产页面都声明了 `lang="en"` 和一个 `<title>` | 3.1.1、2.4.2 | 辅助技术和浏览器标签页都需要这个信息 |
| 每一个交互控件都有可见的焦点指示 | 2.4.7 焦点可见 | 键盘用户需要看到自己所在的位置 |
| 整个构建出来的应用中，颜色对比度都达到 4.5:1 | 1.4.3 对比度（最低要求） | 低对比度的文字，对许多用户来说是不可读的 |
| 每一个表单输入项都有明确的 `type` 和可见的标签 | 1.3.1、4.1.2 | pa11y 的检查工具要求有 `type`；可见的标签是无障碍名称的起点 |
| 状态变化通过一个实时区域播报出来 | 4.1.3 状态消息 | 屏幕阅读器用户需要在不移动焦点的情况下知道发生了什么变化 |

## 性能注意事项

在整个构建过程中定期重新测量绘制调用、三角形数量和页面体积，而不只是在最后测一次——第三阶段已经给了你一套可用的测量方法和一份可以对照的预算。如果超出了预算，就有意识地决定要简化什么，把你第一阶段的「不在范围内」清单作为寻找削减对象的第一个地方。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 在测试任何东西之前就先构建完一切 | 缺陷和无障碍性问题不断累积，最终难以定位、修复成本高昂 | 像第三阶段练习过的那样，每完成一项检查清单任务就测试一次 |
| 只在最后才撰写文档 | 细节被遗忘，README 无法体现出过程中做出的真实决定 | 随着构建过程持续更新变更日志和 README |
| 忽视中期构建复查 | 早期引入的回归问题，要等到其他一切都依赖它们之后才被发现 | 在计划好的检查点处停下来，认真地重新测试 |
| 因为「反正也不难」而添加超出第一阶段计划的范围 | 这个阶段的学习节次还没用完，核心体验就已经赶不上进度了 | 在动手做一个新想法之前，先对照第一阶段的「不在范围内」清单检查一下 |
| 因为构建「看起来完成了」就跳过质量评审 | 陌生人一眼就能发现的问题，构建者自己却注意不到 | 在请求批准之前，完整地完成 `tests/checklist.md` |

## 故障排查

**我的学习节次快用完了。** 回到你的构建检查清单和第一阶段的范围。削减掉尚未完成中最不重要的那一项，并在变更日志和第五阶段的案例分析中记录这次削减——一次诚实、有记录的削减，是软件交付中正常的一部分。

**我每加一个功能，性能预算就往上跑一点。** 每加一次功能就重新测量一次，而不只是在最后测——这样你才能准确抓住是哪一次改动让你超出了预算。

**我不知道 README 和用户指南里分别该写什么。** README 是给要搭建和运行你代码的人看的（一位开发者，未来的你自己）；用户指南是给使用这份完成体验的人看的（你毕业设计真正的受众）。两者很少有太多重叠。

## 拓展挑战

三个拓展挑战，位于 [`challenges/`](challenges/)。基础挑战为必做，另外两个为选做：

1. **[基础](challenges/challenge-1.zh-Hans.md)**：像一个陌生人一样，从一个全新的文件夹开始，照着你自己的 README 走一遍，修复每一处按照文字操作却没能成功的步骤。
2. **[创意](challenges/challenge-2.zh-Hans.md)**：添加一处体现你自己语言或社区的生产细节——一个标签、一段描述、一项交互——并确认它对来自这个社区之外的人来说也能读懂。
3. **[探索](challenges/challenge-3.zh-Hans.md)**：为你的构建流程添加一项基础的自动化检查（哪怕只是一个打开你页面、检查控制台错误的简单脚本），并记录如何运行它。

## 提交作业

1. 完成 [`tests/checklist.md`](tests/checklist.md)。
