# 挑战 3：探索

**进阶选做。** 约 90 分钟。

从中途恢复一个被中断的单一文件，而不只是跳过已经彻底完成的文件。

## 任务

1. 阅读 [MDN: HTTP range requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests)。一个支持它的服务器，会对带有 `Range: bytes=1000-` 请求头的请求，用一个只包含剩余字节的 `206 Partial Content` 响应来回答，并在普通请求上用一个 `Accept-Ranges: bytes` 响应头来宣告自己支持这一点。
2. 在 `download-manager.js` 中，在为一个文件开始一次全新的获取之前，先检查是否已经存在一份*部分*副本（你需要为每个文件新增一条小型的 OPFS 或 Cache API 记录，用来记录「目前已保存的字节数」——`bundle-store.js` 目前的 `saveFile` 只会保存一个完整、已完成的文件，因此这意味着要为进行中的文件添加第二条更小的保存路径）。
3. 如果一份部分副本存在，先发送一个轻量的请求（或者检查一个已缓存响应的响应头），确认服务器依然支持范围请求，并且这个文件没有发生变化，然后只用一个 `Range` 请求头获取缺失的那部分范围，把新的字节追加到这份部分副本上，最后再按照通常的方式保存这个完成的文件。
4. 如果服务器没有发送 `Accept-Ranges: bytes`（用来测试这个项目的 Python `http.server` 就不会发送），就回退到本课现有的行为：重新下载整个文件。
5. 测试它：开始一次下载，在那个更大的文件（`CesiumMilkTruck.glb`）下载到一半时切断连接，重新连接，并（用网络面板）确认，当服务器支持时，恢复的请求只会请求缺失的字节。

## 为什么重要

本课自己的恢复逻辑是在整个文件的层面上运作的：一个在连接断开时已经下载了 90% 的 370 KB 模型，会从零重新开始。范围请求正是真正的生产环境离线交付工具（包括大多数下载管理器和视频播放器）用来避免这种浪费的真实技术——在缓慢或按流量计费的连接上确实很有用，也是一个很好的例子，说明一个浏览器特性只有在你去检测它是否存在时才能真正带来收益，因为不是每一个服务器都支持它。

## 完成标准

- [ ] 当服务器支持范围请求时，一个中途被中断的文件会从它中断的地方继续下载。
- [ ] 对一个不支持它的服务器，回退方案（重新下载整个文件）依然有效。
- [ ] 网络面板显示恢复的请求得到了一个真实的 `206 Partial Content` 响应，并带有一个与实际缺失内容相匹配的 `Content-Range` 响应头。
