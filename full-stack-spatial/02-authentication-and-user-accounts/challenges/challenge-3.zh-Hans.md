# 挑战 3：探索

**进阶选做。** 约 90 分钟。

添加一条账户锁定提示，以及一种无需管理员权限就能测试它的方式。

## 任务

1. 在 `rateLimit.js` 中添加 `msUntilUnlocked(key)`，返回距离 `isRateLimited(key)` 再次变为 `false` 还剩多少毫秒（如果当前没有被限制，则返回 `0`）。
2. 让登录接口的 `429` 响应包含 `{ error, retryAfterSeconds }`，用这个函数计算（向上取整到整数秒）。同时添加一个值相同的 HTTP `Retry-After` 响应头——这是一个真正的标准 HTTP 响应头（[MDN: `Retry-After`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Retry-After)），客户端和代理已经知道该如何读取它。
3. 在 `js/main.js` 中，把这个倒计时显示在登录表单的错误消息里（「尝试次数过多，请在 3:42 后重试。」），并每秒更新一次（这里已经有一个现成的实时区域可以复用——用 `#login-errors`，或者状态横幅）。
4. 添加一个只在测试环境中可用的路由（用 `if (process.env.NODE_ENV === 'test')` 之类的条件加以保护，并在注释中清楚说明它绝不能出现在真实部署中），用来清空某一个键的速率限制器——这正是让 `server.test.js` 能够测试这个倒计时、而不用在每次运行测试时都真的等上 15 分钟的原因。
5. 为新的 `retryAfterSeconds` 字段以及倒计时的边界情况（剩余 0 秒，与依然处于限制中）添加测试。

## 为什么重要

一个没有任何反馈的速率限制，在被它保护的人看来就像是坏掉了一样——连续五次「密码无效」，永远如此，没有任何解释，教不会任何人到底发生了什么。一个可见的、诚实的倒计时是一个很小的用户体验决定，却有着真实的安全价值：它会劝退那种「不断重试」的行为——而这恰恰是这个限制存在的目的——同时又不隐瞒到底发生了什么。这个仅供测试用的逃生通道本身就是一课：那些只是为了让自动化测试成为可能而写的功能，同样需要小心，不能泄漏进生产环境，就像其他任何代码路径一样——课程 5.5 研究的正是这一类错误。

## 完成标准

- [ ] 一个 `429` 响应包含一个 `Retry-After` 响应头和一个 `retryAfterSeconds` 字段，并且在重复请求中能正确倒数。
- [ ] 登录表单会显示并更新一个人类可读的倒计时。
- [ ] 这个仅供测试用的重置路由受到保护、有注释说明，并且在 `NODE_ENV` 不是 `test` 时绝对无法访问。
- [ ] `node --test` 通过，包括针对这个新行为的测试。
