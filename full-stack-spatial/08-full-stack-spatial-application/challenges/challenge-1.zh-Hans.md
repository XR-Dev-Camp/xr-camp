# 挑战 1：基础

**必做。** 约 45 分钟。

给描述草稿接口添加一个速率限制，让一个账户不能连续无限次地请求草稿。

## 任务

1. 打开 `server/rateLimit.js`，重新阅读 `isRateLimited`、`recordFailedAttempt` 和 `clearAttempts` 目前是如何为 `routes.js` 的 `login` 函数中的登录尝试服务的。
2. 在 `describeScene`（`server/routes.js`）中，从账户构建一个速率限制键，例如 `` `describe:${auth.user.id}` ``。
3. 在构建一份草稿之前，用这个键调用 `isRateLimited`。如果已经被限制，就返回状态码 429，以及一条简短的 JSON 错误——和 `login` 已经使用的形式相同。
4. 在一次成功的草稿生成之后，用同一个键调用 `recordFailedAttempt`（即使没有什么真的「失败」，复用这个现有函数依然是复用 `rateLimit.js` 计数器最简单的方式——在一条注释中说明这一点）。
5. 在 `server/server.test.js` 中写一个 `node:test`，快速连续地请求草稿超过限制允许的次数，并断言其中至少有一次请求返回 429。
6. 运行 `npm test`，确认你的新测试和现有的十个测试一起通过。

## 为什么重要

`server/ai.js` 的注释已经指出，一个真实的 AI 服务商每次调用都要付出金钱或时间成本，即使这个结业项目中使用的模拟服务商不需要。一旦一个真实的服务商真的被接入（见探索挑战），对这个接口的速率限制正是「可以安全发布」和「一个有 bug 的客户端脚本在循环中调用这个接口」之间的分界线——即使服务商依然是模拟的，这也是一种良好实践，因为一个没有限制的接口，依然是攻击者可以用来拖慢你服务器速度的又一个东西。

## 完成标准

- [ ] `describeScene` 在同一个账户在短时间内发出过多请求之后返回 429。
- [ ] 一次正常的、偶尔发生的请求依然能成功。
- [ ] 一个新的 `node:test` 证明了这两种行为。
- [ ] `npm test` 完全通过，包括你的新测试。
