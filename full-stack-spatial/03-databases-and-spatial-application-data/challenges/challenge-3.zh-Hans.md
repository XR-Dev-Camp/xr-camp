# 挑战 3：探索

**进阶选做。** 约 90 分钟。

让一个场景的所有者能邀请另一个账户作为**协作者**，这个协作者可以编辑场景的物体和注释，但绝不能删除这个场景，也不能移除所有者的访问权限——这是本模式目前还没有的一种全新关系。

## 任务

1. 用一次迁移设计一张关联表 `scene_collaborators`：`scene_id` 和 `user_id`，两者都是带 `ON DELETE CASCADE` 的外键，并设置一个复合主键 `(scene_id, user_id)`，这样同一个人就不能被添加两次。这是对多对多关系（一个场景可以有多个协作者；一个账户可以协作多个场景）建模的标准方式——单独的 `scenes` 或 `users` 都无法承载它。
2. 添加 `db.js` 函数：`addCollaborator(sceneId, userId)`、`removeCollaborator(sceneId, userId)`、`listCollaborators(sceneId)` 和 `isCollaborator(sceneId, userId)`。
3. 添加一个路由（仅限所有者，经过 CSRF 检查），用于按用户名添加一个协作者，再添加一个用于移除一个协作者的路由。
4. 修改 `updateScene`、`addAnnotation` 和 `removeAnnotation` 中的权限检查（但刻意**不**修改 `removeScene`），让协作者也能通过，而不仅仅是所有者。在一条注释中准确写明，为什么即使有了这个功能，`removeScene` 也应该继续仅限所有者。
5. 添加一个小的界面：所有者可以输入并添加一个协作者的用户名；一个协作者能看到一个用于添加注释的「Add」表单，以及被启用的变换控件，但永远看不到删除场景的按钮。
6. 添加测试：一个协作者可以编辑物体并添加注释；一个协作者不能删除场景，也不能添加另一个协作者；删除一个协作者的账户（`DELETE /api/account`）会移除他们的 `scene_collaborators` 行，但不会触及场景本身。

## 为什么重要

几乎每一个真实的空间或协作类应用，最终都需要在同一份数据上有不止一个编辑者——这正是关联表和一个略微丰富一些的权限检查所要解决的建模问题，也是课程 5.4 接下来要构建的共享多用户房间的一次直接、动手的预演。

## 完成标准

- [ ] `scene_collaborators` 存在，两个外键都设置了 `ON DELETE CASCADE`，并有一个复合主键。
- [ ] 一个协作者可以编辑一个场景的物体和注释，但不能删除这个场景，也不能添加另一个协作者。
- [ ] 删除一个协作者的账户会移除他们的 `scene_collaborators` 行，但场景本身及其其他数据不受影响。
- [ ] 新增的测试覆盖了以上全部三个权限边界，并且 `node --test` 通过。
