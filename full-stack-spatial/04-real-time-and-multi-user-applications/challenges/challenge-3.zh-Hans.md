# 挑战 3：探索

**进阶选做。** 约 90 分钟。

添加第二个房间，以及一种在它们之间移动的方式。

## 任务

1. 在 `server/rooms.js` 的 `KNOWN_ROOMS` 中添加第二个条目（例如 `'quiet-corner'`），并在 `index.html` 中添加一个小小的 `<select>` 或一对按钮，让人可以在连接之前（或之后）选择一个房间。
2. 在 `js/net.js` 中，支持在不完全重新加载页面的情况下切换房间：干净地 `stop()` 当前连接（发送一次真正的关闭，而不只是丢弃这个套接字），并用新的房间名打开一个新连接。决定并在一条注释中记录下来：属于旧房间的状态会发生什么——花名册和聊天记录应该被清空，还是学习者应该能切换回去再次看到它们？
3. 在服务器上，确保一个切换房间的成员会从旧房间的在场名单中被移除（那里会触发一个 `leave` 事件），并被添加到新房间的在场名单中（那里会触发一个 `join` 事件）——`handleConnection` 现有的生命周期假设一个连接在其整个生命周期内只属于一个房间，因此在这个设计中切换房间意味着关闭一个 WebSocket 并打开一个新的，这自然会为旧房间触发 `leaveRoom` 的清理，并为新房间触发 `joinRoom` 的设置。
4. 添加一个短暂存在的「近期活跃房间」指示器：在服务器内存中追踪 `KNOWN_ROOMS` 中每一项当前有多少成员，并把它暴露出来——一个简单的 `GET /api/rooms` HTTP 路由，返回 `[{ roomId, memberCount }]`，就足够了；这部分不需要 WebSocket。
5. 至少写一个测试，证明一个从一个房间「移动」到另一个房间的成员，会停止接收前一个房间的消息，并开始接收后一个房间的消息。

## 为什么重要

任何超越单一固定房间的真实聊天或在场系统，都必须回答这个挑战提出的同一个问题：当一个连接所*连接到*的东西发生变化时，这个连接的身份和状态会发生什么？这没有唯一正确的答案——关闭并重新打开连接（这个挑战采用的方法）比让一个连接在多个房间之间保持存活更容易推理，代价是会有一次可见的重新连接。自己去理清这个权衡，而不是被直接告知答案，正是一个「探索」挑战的意义所在。

## 完成标准

- [ ] 至少存在两个房间，学习者可以在界面上选择其中之一。
- [ ] 切换房间能正确地把一个成员从旧房间的花名册中移除（对那里的其他每一个人来说），并把他们添加到新房间的花名册中。
- [ ] `GET /api/rooms` 为每个房间返回一个准确的成员数。
- [ ] 一个新的自动化测试覆盖了切换房间的情况，并且 `node --test` 通过。
