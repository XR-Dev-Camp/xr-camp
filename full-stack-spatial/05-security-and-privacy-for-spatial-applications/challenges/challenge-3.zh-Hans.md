# 挑战 3：探索

**进阶选做。** 约 90 分钟。

为聊天和注释创建添加一个真正的按连接速率限制，采用课程 5.4 的 `realtime.js` 已经为位置更新使用过的那种形式。

## 任务

1. 重新阅读课程 5.4 的 `realtime.js`（`full-stack-spatial/04-real-time-and-multi-user-applications/completed/server/realtime.js`）——特别是 `POSITION_MIN_INTERVAL_MS`，以及 `handlePosition` 如何在验证或广播任何内容*之前*就先检查它。
2. 在本课的 `completed/server/realtime.js` 中，给聊天处理函数添加一个滑动窗口速率限制：例如每个连接每 10 秒不超过 5 条消息（5.4 的 `CHAT_WINDOW_MS`/`CHAT_MAX_MESSAGES` 模式是一个合理的参考模型），一旦超出就通过 WebSocket 返回一条清晰的 `error` 消息——而不是悄无声息地丢弃这条消息、不给出任何反馈。
3. 给 `routes.js` 中的 `createAnnotation` 添加一个等效的限制（一个已登录账户留下注释的速度，不应该超过一个真实的人可能达到的速度）。
4. 为这两个限制都编写 `node:test` 断言：以超过限制的速度发送消息/注释，并断言一旦达到限制，服务器就会（通过 WebSocket）返回一个错误，或者（通过 HTTP）返回一个 `429`；而更慢的节奏则永远不会被拦截。
5. 在你的学习日志中，把这个修复和挑战 1 的修复（如果你做了的话）做个比较：对一条 WebSocket 消息做速率限制、和对一个 HTTP 请求做速率限制，有什么不同？为什么 5.4 的位置同步限制要在验证消息内容*之前*就先检查速率？

## 为什么重要

一个实时连接不像一次表单提交那样，在消息之间存在天然的停顿——没有任何东西能阻止一个被修改过的客户端（或者一个脚本，而不是一个浏览器）以网络允许的最快速度发送消息。这正是课程 5.4 已经应用于位置更新的同一个原则；这个挑战要求你注意到，它从未被应用到本课自己的聊天和注释功能上，并以同样的方式——在服务器上、独立于任何一个行为良好的客户端自己已经做过的事情——修复这个缺口。

## 完成标准

- [ ] 超过你选定限制的聊天消息会收到一条清晰的错误，而不是沉默。
- [ ] 超过你选定限制的注释会收到一个 `429`。
- [ ] `node:test` 证明了这两个限制都有效，并且正常、更慢节奏的使用永远不会被误判拦截。
- [ ] 一段简短的学习日志笔记，比较了这个修复和对一个 HTTP 接口做速率限制的区别。
