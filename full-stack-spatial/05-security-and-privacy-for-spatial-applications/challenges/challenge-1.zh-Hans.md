# 挑战 1：基础

**必做。** 约 45 分钟。

添加一个本课尚未涵盖的第八个审查目标——创建场景和注释时缺失的一个速率限制——以及一个证明你已经修复它的 `node:test`。

## 任务

1. 在 `completed/server/` 中，注意到 `createScene` 和 `createAnnotation`（在 `routes.js` 中）完全没有任何速率限制：一个已登录的账户可以想创建多少场景或注释就创建多少，想多快就多快。课程 5.2 的 `rateLimit.js`（原样延续到本课）已经给了你 `isRateLimited`、`recordFailedAttempt` 和 `clearAttempts`——和 `login` 已经在用的是同一批函数。
2. 给 `createScene` 和 `createAnnotation` 添加一个速率限制：一个合理的上限（例如，每个账户每 15 分钟 10 个场景或注释——可以复用 `rateLimit.js` 现有的时间窗口，也可以选择并说明你自己的窗口），一旦超出就返回带有清晰消息的 `429`，和 `login` 已经用于处理重复失败尝试的形式相同。
3. 在 `server.test.js` 中写一个 `node:test`，创建场景直到超出你的限制，并断言服务器最终会回应 `429`。
4. 更新 README 的威胁模型表格：一个*不受限制*的创建接口属于哪一个 STRIDE 类别？为什么本课最初的那七个没有包含它？

## 为什么重要

一个没有对写入接口做速率限制的已登录账户，依然能造成真实的危害——用垃圾数据填满数据库、推高存储成本，或者把这个应用当作一个针对其他会读取它所创建内容的用户（比如 `getScene` 的注释列表）的垃圾信息中继站。本课程中每一节其他有可能被这样滥用的课（登录尝试、聊天、位置更新）都已经有了限制；这个挑战要求你注意到、并关闭本课自己这次审查所遗漏的那一个。

## 完成标准

- [ ] `createScene` 和 `createAnnotation` 在超出你选定的限制后都会返回 `429`，并附带一条使用真实应用的学习者能够理解的消息。
- [ ] 一个新的 `node:test` 证明了这一点，并且 `npm test` 依然完全通过。
- [ ] README 的威胁模型表格中有了一个新的（或者被更新过的）行，说明了这个威胁。
