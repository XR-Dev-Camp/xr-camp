# AI 作为开发助手

**Language / Idioma / 语言:** [English](README.md) · [Español](README.es.md) · [简体中文](README.zh-Hans.md)

**课程：** `frontend-engineer` · **课时：** `ai-as-a-development-assistant-08` · **时长：** 约 10 小时 · 14 次学习，每次 45 分钟 · 每周 4 次，约 4 周

---

> 完成并记录一次 AI 辅助的代码审查，同时不放弃自己的理解。

---

## 学习目标

完成本项目后，你将能够：

1. 选择一个在你所在地区可用的 AI 助手：一个云端服务、一个中国的 AI 助手，或者你自己电脑上的一个**本地模型**。
2. 判断你可以和一个 AI 助手**分享**什么，以及绝不能粘贴什么：机密信息、个人数据，以及你没有权利分享的代码。
3. 让**理解始终排在第一位**：在提问之前先用自己的话解释代码，在运行之前先做出预测，并且要求解释，而不只是要求修复方案。
4. 用一手资料（MDN、某个规范，或某个库的官方文档）**核实**AI 助手说的每一条论断，并识别出不存在的 API。
5. 给每一条建议一个**结论**（采纳、修改，或拒绝），并附上依据，同时如实记录你是如何使用 AI 的。
6. **亲自**用键盘和屏幕阅读器测试无障碍性，因为一个只读代码的助手听不到屏幕阅读器实际会说什么。
7. 比较一个助手用英语、西班牙语和中文回答问题的质量。

## 你将构建什么

这次不是 **My XR Camp** 的一个新部分：而是一次记录完整的 **AI 辅助代码审查**，回顾的是第三部分——你在课程 2.3 中做的那个学习计划器。

你会请一个 AI 助手解释并审查你代码中的一小部分，并核实每一条回答。你会记录下你问了什么、它说了什么、你核实了什么、你的依据来源、你的结论，以及你学到了什么。最后，你会把这次审查发布成一个小巧、无障碍的网页，并保留一份**AI 使用记录**，记录每一次你使用助手的情况。

重点不在于助手给出的答案，而在于你能对这些答案证明什么。

[`completed/`](completed/) 中的参考答案是 Ana 的审查记录，包含七个条目（两个采纳、两个修改、三个拒绝），以及她做出的两处改动。起始代码包含学习计划器、审查记录和使用记录的模板、一个关于虚构 API 的练习，以及带有十四个 TODO 的审查页面。

### 第 1 步：规则先行（TODO 1）

**AI 助手**是一个在海量文本和代码上训练出来的程序。它会根据你写的内容预测一个可能的答案。它常常很有用，也常常会出错——而且是用同样自信的口吻说出错误答案的。除非工具明确说明它会去查找资料，否则它并不会真的去查任何东西，即使查了，也可能会误读查到的内容。

在向它粘贴任何内容之前，先定好你的规则。把它们写在 `ai-log.md` 的开头：

- **绝不粘贴机密信息**：密码、API 密钥、令牌、`.env` 文件、私钥。除非条款明确说明并非如此，否则要假设你粘贴的任何内容都会被存储，可能被公司内部的人看到，也可能被用来训练未来的模型。
- **绝不粘贴个人数据**：姓名、邮箱、电话号码、地址，或任何人已保存的数据。你计划器中已保存的学习时段也属于个人数据。
- **只粘贴你有权分享的代码**：你自己的代码，或者许可证允许分享的代码。未经许可，不要粘贴同学的代码，也不要粘贴雇主或客户的代码。
- **遵循你所在学校或雇主的规则。** 许多机构都有自己的 AI 政策。如果它比你自己的规则更严格，就以它为准。如果不确定，就去问一问。
- **说明 AI 在哪里帮了忙。** 在本课中，这份记录本身就承担了这个作用。在你的作品集中，一句话就够了：「我使用了一个 AI 助手来审查这段代码，并核实了它的每一条建议。」

**AI 写的代码归谁所有？** 这取决于所在的国家，而相关法律仍在变化之中。每个助手的使用条款都会说明它们允许什么。生成的代码有时可能会和某段已有自己许可证的现有代码高度相似。安全的做法是：让生成的片段保持简短，理解每一行代码，并说明 AI 在哪里帮了忙。

### 第 2 步：选择一个助手（TODO 2）

大致有三种类型。任何一种都能用于本课。

| 类型 | 例子 | 值得了解的一点 |
| --- | --- | --- |
| **西方公司的云端服务** | ChatGPT、Claude、Gemini、Microsoft Copilot | 运行在这些公司自己的电脑上。许多在中国大陆无法访问。 |
| **中国公司的云端服务** | 千问（原通义）、DeepSeek、Kimi、豆包 | 通常在中国大陆可以访问，中文表现往往不错。有些从其他地区访问可能会比较困难。 |
| **本地模型**，运行在你自己的电脑上 | 用 Ollama 或 LM Studio 运行一个开放权重模型 | 你输入的任何内容都不会离开你的电脑，下载完成后就能离线使用。需要一台较新的、内存充足的电脑；模型体积往往有好几个 GB。较小的模型出错更多。 |

许多服务都提供免费额度；请查阅当前的条款，包括任何最低年龄要求。哪些服务可以访问、需要多少费用，会经常变化，也因国家而异，所以要查一查在你所在的地方、在今天，哪些是可用的。有些助手也能在你的代码编辑器中直接使用；但对本课来说，一个聊天窗口就够了，因为你需要看到并记录下每一个问题。

没有哪个助手总是对的，也没有哪个是「安全」的那一个。本课的方法对所有助手都是一样的。

在 `ai-log.md` 中，写下你选择了哪个助手、为什么，并添加你的第一条记录。从现在起，记录每一次对话：日期、使用的助手、你请求了什么、你分享了什么，以及你保留了什么。

### 第 3 步：先自己读懂代码（TODO 3–4）

**理解永远排在第一位。** 如果你在阅读之前就先提问，你就无法分辨一个答案是好是坏。

选择一个**小**部分：一到两个文件，大约 200 行以内。Ana 选择了 `store.js` 和 `main.js`。把你的范围写在 `review.md` 的开头（TODO 3）。

然后在没有打开任何助手的情况下阅读你的文件，并用自己的话解释它们（TODO 4）。对 `store.js` 而言：它保存了什么？谁可以修改它？当有人按下**完成**时，按顺序会发生什么？把你不理解的地方都记录成问题。这些问题会成为你最初的提示词（prompt）。

### 第 4 步：要求解释（TODO 5）

现在打开助手。四个习惯能让你始终掌握主动权：

1. **小提示词。** 一个问题，一段代码。「解释这个函数」比「审查我的整个应用」要好得多。
2. **要求解释，而不只是要求修复。** 「为什么这样能行得通？」能教会你东西。「帮我修复它」只会给你一段不是你自己写的代码。
3. **把它讲回去。** 得到答案后，不看着答案，用自己的话把它写出来。如果做不到，就换一种方式再问一次。
4. **运行之前先预测。** 在测试一条论断之前，先写下你预期会发生什么。然后再运行它。一个错误的预测，正是学习真正发生的地方。

一个好的初始提示词看起来是这样的：

```text
I am learning JavaScript. Here is one function from my own project.
Explain what the line with || does, step by step, with an example.
Do not rewrite the code.

export function bySchedule(a, b) {
  return DAYS.indexOf(a.day) - DAYS.indexOf(b.day) || a.time.localeCompare(b.time);
}
```

你可以在浏览器的**控制台**中测试真实页面里的代码。在计划器页面上，这样做会加载和页面完全相同的 store：

```js
const store = await import('./js/store.js');
const stop = store.subscribe((sessions) => console.log('Now', sessions.length));
```

添加一个学习时段，观察这条消息。然后调用 `stop()`，再添加一个，观察什么都不会发生。

填写两条审查条目（TODO 5），每个问题对应一条。每一条都包含六个部分：**我问了什么**、**它说了什么**、**我核实了什么**、**依据来源**、**结论**，以及**我学到了什么**。

| 结论 | 含义 |
| --- | --- |
| **采纳** | 已核实、正确，并且原样使用了。 |
| **修改** | 部分正确：你在修正或调整之后使用了它。 |
| **拒绝** | 错误、虚构，或不适用于这段代码，并且你能证明为什么。 |

「已核实」指的是你能够指出来的东西：一个文档页面、一份规范、一次你自己运行的测试，或者一个你比较过的预测结果。「听起来是对的」不算核实。

### 第 5 步：虚构的 API（TODO 6–7）

助手有时会**虚构**一些东西：一个不存在的方法、一个任何函数都不接受的选项，或者一条关于浏览器行为的、根本不成立的规则。它通常看起来和真正的代码一模一样，还带着一个听起来很合理的名字。这种现象常常被称为**幻觉（hallucination）**。

打开 [`starter/invented-apis.md`](starter/invented-apis.md)。这是一份关于这个计划器的「AI 回答」，**由 XR Camp 编造出来作为练习示例**，包含四条论断。其中一些是错的。针对每一条（TODO 6）：

1. 在 **MDN**（developer.mozilla.org）上查找这个方法或行为。MDN 用多种语言记录了 Web 标准，包括西班牙语和中文。
2. 用你自己的话写下 MDN 是怎么说的，并链接到对应页面。
3. 给出你的结论。

然后在控制台中测试每一条论断（TODO 7）。三个快速测试：

```js
'focusNext' in HTMLElement.prototype   // 这个方法到底存不存在？
localStorage.getItem('no-such-key')    // 对一个不存在的键会得到什么？
[3, 1, 2].sort((a, b) => a - b, { copy: true })   // 多传一个参数会有任何效果吗？
```

注意第三个例子。JavaScript 会默默忽略多余的参数，所以一个虚构出来的选项**不会引发任何错误**。代码照样运行，只是悄悄地做了错误的事。这正是为什么「它运行了」不等于「它是对的」。

### 第 6 步：请求一次审查（TODO 8）

现在请助手一次审查一个文件：

```text
Review this JavaScript module from my own learning project.
List possible bugs, security problems, and unclear code.
For each one, say how confident you are, and why.
Explain; do not rewrite the whole file.
```

针对每一个发现，写一条审查条目（TODO 8）：至少再写三条。有些发现在一般情况下是成立的，但在你的代码中并不成立。Ana 的助手警告说，如果某个 id 不存在，`toggleSession` 就会崩溃。这话没错，但在她的计划器中，每一个 id 都来自前一刻从 store 中绘制出来的按钮。了解你自己的代码，正是让你能够说出「这里不适用，理由是……」的原因。

然后应用你采纳或修改后的内容，**每次改动一个提交**，并在每次改动后运行 `check.html`。如果某项检查失败了，你能准确知道是哪次改动造成的：`git restore` 那个文件，或者 `git revert` 那次提交。

### 第 7 步：有 AI 辅助和没有 AI 辅助的无障碍检查（TODO 9）

问问助手：「这个表单无障碍吗？使用屏幕阅读器的人会听到什么？」记录下它的回答。这可能会有用，但也可能是错的，因为助手读的是代码，而无障碍性关乎的是人们实际的体验。

然后自己去测试它：

1. **只用键盘。** 拔掉鼠标，或者干脆不碰它。添加一个学习时段，把它标记为完成，再删除它。你能始终看清焦点在哪里吗？
2. **屏幕阅读器。** 打开 NVDA、VoiceOver，或 TalkBack。做同样的三件事。然后在空的主题输入框中按下**回车键**。你听到了什么？

把助手说的话和你实际发现的内容并排写下来（TODO 9）。Ana 的助手说这个表单「看起来是无障碍的」。而她的屏幕阅读器在她于空的主题输入框中按下回车时什么都没说，因为焦点当时已经在那里了。参见她审查记录中的第 7 条。

### 第 8 步：其他语言（TODO 10）

助手往往在英语上受到的训练比其他任何语言都多，所以它们用其他语言给出的回答可能会更弱，或者只是有所不同。用西班牙语、中文，或者你自己的语言，重新问一遍你之前问过的某个问题。比较一下：

- 这个解释依然**正确**吗？
- 技术词汇被翻译了，保留了英文，还是混用了？对照那种语言下的 MDN 检查一下这些词。
- 代码是一样的吗？注释被翻译了吗？
- 你更愿意从哪个答案中学习？

把你的比较写进 `review.md`（TODO 10）。这里没有正确答案：你是在收集证据。

### 第 9 步：发布审查记录（TODO 11–13）

`index.html` 把你的审查记录变成一个别人也能阅读的页面。它包含：

- 一张**摘要表格**：每条审查条目一行，附上它的结论。在窄屏幕上，表格会在自己的方框内横向滚动，而页面本身不会。这个方框可以获得键盘焦点，因此不用鼠标也能滚动它。
- **每个条目一个小节**，六个部分放在一个描述列表（`<dl>`）中。
- 结论用**文字**表示，并配有边框。颜色只是起辅助作用。
- 任何用其他语言写的引文都标注了 `lang`，例如 `<span lang="es">`，这样屏幕阅读器就能正确地朗读它。

填写表格（TODO 11）和各个小节（TODO 12）。然后用你学到的东西完成 `review.md`（TODO 13）：助手做得好的地方是什么，它错在哪里，下次你还会用同样的方式使用它吗？

## 关键代码解析

**控制台中的 `await import('./js/store.js')`。** 动态导入可以从控制台加载一个模块。因为页面已经加载过同一个文件，你会得到**同一个**模块、同样的状态，这样你就可以测试真实的 store。

**`'focusNext' in HTMLElement.prototype`。** 每个元素的方法都存在于它的原型上。`in` 问的是「这个名字是否存在于其中的任何地方？」。`false` 意味着你正在使用的浏览器没有这个方法，不管助手怎么说。去 MDN 上查一查，是否有任何浏览器拥有它。

**`<div class="table-scroll" role="region" aria-labelledby="summary-caption" tabindex="0">`。** `tabindex="0"` 让使用键盘的人能够聚焦这个方框，并用方向键滚动它。带有名称的 `role="region"` 会告诉使用屏幕阅读器的人,他们停留在了什么地方。

**`<th scope="col">` 和 `<th scope="row">`。** 分别是列和行的表头，这样屏幕阅读器就能在你浏览表格时说出「Verdict: Rejected」这样的内容。

**3D 时刻中的 `THREE.MathUtils.degToRad(30)`。** three.js 用弧度来度量旋转；完整一圈是 `2 * Math.PI`。`degToRad` 让你可以按照你脑中想的角度来书写。

## 3D 时刻

打开 [`starter/3d-moment.html`](starter/3d-moment.html)：一个紫色的环面纽结，从右上方打光，缓缓旋转。下面是代码，以及一份关于这段代码的「AI 解释」，**由 XR Camp 编造出来**供你练习。它的七条论断中有一些是错的。

对照 [threejs.org/docs](https://threejs.org/docs/) 上官方的 three.js 文档，核实每一条论断（TODO 14）。搜索类名，比如 `DirectionalLight`，阅读它的描述。在可能的情况下，也去测试一下这条论断：改变一个值，重新加载，观察，再改回去。试试把 `MeshStandardMaterial` 换成 `MeshBasicMaterial`，或者移除 `degToRad`。如果没做这些检查，你会安心地看着这个结果吗？

three.js 是一个库，不是一个 Web 标准，所以 MDN 不会记录它：它自己的文档才是一手资料。然后和 [`completed/3d-moment.html`](completed/3d-moment.html) 比较一下，看看 Ana 是如何核实每一条论断的。

最后，真的去做一遍：请你自己的助手解释同样的代码，记录这次对话，并用同样的方式核实它的回答。

这个场景会用文字描述自己，如果你要求设备减少动态效果，它会以静止状态开始，并带有一个**暂停动画**按钮，可以完全停止动画循环。

## 无障碍要求

| 要求 | WCAG 2.2 | 原因 |
| --- | --- | --- |
| 摘要表格有标题，以及列和行的表头 | 1.3.1 | 这个结构对屏幕阅读器是可用的，而不只是视觉上可见。 |
| 表格的滚动方框可以获得焦点，并且有名称 | 2.1.1, 4.1.2 | 使用键盘的人可以滚动它，并且知道它是什么。 |
| 在 320 CSS 像素宽度下页面本身绝不会横向滚动；只有表格的方框可以 | 1.4.10 | 数据表格是重排（reflow）所允许的少数例外之一。 |
| 结论用文字表示，颜色只是第二重信号 | 1.4.1 | 没有人必须依靠区分绿色和红色。 |
| 其他语言的引文标注了 `lang` | 3.1.2 | 屏幕阅读器会切换发音方式。 |
| 标题按顺序排列：一个 `h1`，`h2` 表示各节，`h3` 表示各条目 | 1.3.1 | 人们可以按标题在审查记录中跳转。 |
| 计划器的错误会被朗读 | 3.3.1, 4.1.3 | Ana 的第 7 条：这条消息也必须传达给使用屏幕阅读器的人。 |
| 3D 场景有文字描述，可以暂停，并遵循减少动态效果的设置 | 1.1.1, 2.2.2 | 信息和动效绝不会被强加给任何人。 |

## 性能注意事项

**本地模型**使用的是你自己的处理器和内存。在较旧的笔记本电脑上，回答可能会很慢，你的其他程序也会变得更慢。关闭不需要的程序，如果模型运行吃力，就换一个更小的模型。云端服务几乎不占用你电脑的资源，但需要网络连接。

助手给出的建议也不是没有成本的。检查一下它们给你的页面添加了什么：一个「只为了这个功能」而引入的新库、同一个函数的第二份副本，或者在每次渲染时都添加一个监听器。除了问「它能用吗？」，也要问「这需要付出什么代价？」。

3D 时刻是按照「速度 × 距上一帧经过的秒数」来旋转的，所以在 60 Hz 和 120 Hz 的屏幕上旋转速度是一样的。**暂停**会给 `setAnimationLoop` 传入 `null`，所以在静止状态下完全不会绘制任何帧。

## 常见错误

| 错误 | 会发生什么 | 应该怎么做 |
| --- | --- | --- |
| 粘贴整个项目 | 得到冗长、含糊的回答，可能还有你没注意到的机密信息 | 每次只粘贴一小段 |
| 要求「帮我修好它」 | 你得到的是一段自己无法解释的代码 | 先问为什么，然后自己去修复 |
| 「它运行了，所以它是对的」 | 虚构出来的选项会悄悄地失败 | 核实文档，并测试它应有的行为 |
| 信任一个语气自信的回答 | 错误的回答听起来同样自信 | 每一条论断都需要一个依据来源 |
| 在一次提交中接受多处改动 | 一旦出错，你无法分辨是哪一处 | 每次改动一个提交 |
| 没有依据就拒绝 | 你的结论只是一种个人看法 | 链接到相关页面，或者展示测试结果 |
| 因为 AI 说「无障碍」就跳过屏幕阅读器测试 | 真实存在的障碍依然存在 | 用人们真正使用的工具去测试 |
| 只记录好的回答 | 这份记录就不再诚实了 | 记录每一次使用，包括没用的那些 |

## 故障排查

**我想用的助手在我所在的地区不可用。** 试试第 2 步中另一类里的助手，或者一个本地模型。如果都不行，一位同学、导师，或学习小组可以扮演助手的角色：他们回答你的问题，你用完全相同的方式去核实。

**本地模型非常慢，或者根本启动不了。** 在 Ollama 或 LM Studio 中选一个更小的模型，关闭其他程序，检查一下你的可用磁盘空间。

**助手拒绝回答，或者给出的回答非常简短。** 把提示词变小一点，说明你正在学习，只粘贴和问题相关的那段代码。

**MDN 上完全没有提到这个方法。** 这也是一种证据。先在 MDN 上搜索，再在控制台中用 `in` 测试一下。如果两边都没有结果，那这个方法几乎可以肯定是不存在的。

**在控制台中 `await import(...)` 失败了。** 要在计划器页面本身上运行它，通过 `http://` 提供服务，并检查路径：`./js/store.js` 是相对于页面的路径。

**改动之后 `check.html` 失败了。** 恢复这个文件（`git restore planner/js/utils.js`），再重新看看那次改动做了什么。

## 标准聚焦

当你核实一个助手的说法时，你需要一个可以据以**核实**的东西。对于 Web 而言，那就是各种标准：WHATWG 的 **HTML** 和 **DOM** 标准（`focus()`、`localStorage`）、Ecma International 的 **ECMAScript**（`Array.prototype.sort`），以及 W3C 的 **WCAG** 和 **WAI-ARIA**。MDN 会记录它们，并附有关于哪些浏览器支持每个功能的说明。如果一个方法既不在标准中、也不在 MDN 上，那就没有任何浏览器有义务实现它。

W3C 也在关注 AI 本身。它 2024 年的团队报告《AI & the Web》讨论了机器学习模型对 Web 的影响，以及未来标准工作可能涉及的领域。这是一份报告，不是一项标准。W3C 的 **Web Machine Learning Working Group** 正在开发用于在浏览器中运行机器学习模型的 API。
